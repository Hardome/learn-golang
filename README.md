# Урок 023. Модули

Модуль — это набор Go-пакетов, которые хранятся в одном дереве каталогов и выпускаются под общей версией.
У модуля есть путь, например `github.com/Hardome/learn-golang`. В корне модуля лежит файл `go.mod`.
Проще всего увидеть разницу на примере проекта с командой `main` и пакетом `greeting`. Это два пакета,
но оба могут входить в один модуль. Как устроены пакеты, разобрано в [уроке 022][packages-lesson].

Этот урок сам является модулем. В корне уже есть [go.mod](go.mod), [hello.go](hello.go) и [greeting.go](greeting.go).
Для пробного запуска выполните `go run .`. Примеру достаточно стандартной библиотеки.

## Зачем нужны модули

- **Независимые проекты.** Один проект может использовать версию `v1.2.0` библиотеки, другой — `v1.5.0`.
  Go выбирает версии для каждого проекта отдельно. Обе версии могут лежать в одном кеше модулей.
- **Повторяемый выбор зависимостей.** Когда другой разработчик берёт те же исходники и те же файлы модуля,
  Go выбирает версии по тем же требованиям и сверяет скачанное содержимое с контрольными суммами.
- **Управление версиями.** Можно указать нужную версию, обновить только выбранную зависимость или временно
  подключить свою копию библиотеки с диска.
- **Публикация.** Модуль с библиотечными пакетами можно опубликовать через репозиторий и подключать в других проектах.
  Go умеет получать модули через прокси и напрямую из систем контроля версий.

## Что лежит в go.mod и go.sum

### go.mod описывает модуль и его требования

В минимальном `go.mod` есть две строки.

```go
module github.com/Hardome/learn-golang

go 1.24.4
```

`module` задаёт путь модуля. У пакета в его корне такой же путь импорта, а у пакета в папке `greeting` к нему
добавляется `/greeting`. Строка `go 1.24.4` задаёт минимальную версию Go для этого модуля. Более новая версия
тоже подходит. Начиная с Go 1.21 это обязательное требование. Если установленный Go старее, команда `go` может
выбрать более новый инструмент, когда это разрешает настройка `GOTOOLCHAIN`. Иначе она сообщит об ошибке.
Необязательная строка `toolchain` задаёт рекомендуемую версию инструмента для работы с главным модулем.

Когда проект использует стороннюю библиотеку, в `go.mod` появляется `require`. Например, такой может быть часть
файла в проекте, который импортирует пакет `rsc.io/quote`.

```go
require rsc.io/quote v1.5.2
```

Эта строка означает «для модуля `rsc.io/quote` нужна версия как минимум `v1.5.2`». Если другая зависимость
запросит более высокую версию того же модуля, Go учтёт и это требование. Строки с пометкой `// indirect`
обычно означают, что ни один пакет проекта не импортирует пакет из этого модуля напрямую. Например,
библиотека может использовать другую библиотеку внутри себя.

### go.sum хранит контрольные суммы

При загрузке Go сверяет содержимое зависимости с контрольной суммой. Если содержимое одной и той же версии
изменилось и сумма больше не совпадает, Go остановится с ошибкой. При первом скачивании публичного модуля Go
обычно сверяет сумму с публичной базой контрольных сумм. Известные суммы сохраняются в `go.sum`.

Запись с окончанием `v1.5.2/go.mod` относится только к файлу `go.mod` зависимости. Запись с `v1.5.2` относится
к файлам модуля. Поэтому для одной версии можно увидеть две записи. В `go.sum` также иногда остаются суммы
других версий, например если Go читал их `go.mod` при расчёте зависимостей.

Список выбранных версий показывает `go list -m all`. `go.sum` нужен для проверки содержимого. Обычно оба
файла хранят в Git. Если проект использует только стандартную библиотеку, как этот урок, `go.sum` может
вообще не появиться.

## Как создать модуль

Для этого примера откройте терминал в отдельном рабочем каталоге. Создайте папку `hello` и перейдите в неё.

```text
mkdir hello
cd hello
go mod init example.org/hello
```

`go mod init` создаст `go.mod` в текущей папке и сообщит `go: creating new go.mod: module example.org/hello`.
Домен `example.org` здесь нужен только для примера. Для запуска программы с одной стандартной библиотекой
публиковать проект или подключаться к этому домену не нужно. Для локальной тренировки можно также указать
короткий путь и выполнить `go mod init hello` вместо команды выше. Имя папки и путь модуля могут отличаться.
Версию в строке `go` команда подставит на основе запущенного инструмента.

Создайте рядом файл `main.go`.

```go
package main

import "fmt"

func main() {
    fmt.Println("Привет, Go!") // Привет, Go!
}
```

Обе команды запустят этот пример и выведут `Привет, Go!`.

```text
go run main.go
go run .
```

В первой команде указан конкретный файл. Во второй точка означает «пакет из текущей папки».
Чтобы собрать исполняемый файл, выполните `go build .`. В этом примере результат называется `hello.exe`
на Windows и `hello` на Linux и macOS. Для пакета в корне имя берётся из последней части пути модуля.
Если путь заканчивается на `/v2` или другой суффикс мажорной версии, Go пропустит этот суффикс при выборе имени.
С помощью флага `-o` можно задать имя самому.

### Как выбрать путь для проекта в Git

Если проект будет жить на GitHub, обычно в качестве пути модуля берут адрес репозитория без `https://`
и без `.git`. Например, для нового проекта команда может выглядеть так.

```text
go mod init github.com/your-username/your-project
```

Команда создаёт только `go.mod`. Репозиторий, публикация и выпуск версии — отдельные действия.
Если в одном репозитории несколько самостоятельных модулей, у каждого свой `go.mod` и свой путь.

### Как запустить пакет из нескольких файлов

В рабочем примере урока `hello.go` объявляет функцию `sayHello` и точку входа `main`.

```go
func sayHello(name string) {
    fmt.Printf("Привет, %s!\n", name) // Подставляет имя в приветствие.
}

func main() {
    sayHello("Go") // Привет, Go!
}
```

Файл `greeting.go` объявлен в том же пакете и вызывает эту функцию при запуске.

```go
package main

func init() {
    sayHello("читатель") // Привет, читатель!
}
```

Из корня ветки можно запустить весь пакет, не перечисляя файлы.

```text
go run .
go build .
```

`go run .` выведет сначала `Привет, читатель!`, затем `Привет, Go!`. `go build .` соберёт тот же пакет в
`learn-golang.exe` на Windows или `learn-golang` на Linux и macOS. Если выполнить `go run hello.go`, Go возьмёт
только указанный файл, и на экране будет одна строка — `Привет, Go!`.

## Как работать с зависимостями

Команды ниже можно попробовать в папке `hello`, созданной выше. Для команд с внешними модулями нужен доступ
к источнику зависимостей, если нужных данных ещё нет в кеше.

### Добавить зависимость

В `main.go` можно подключить пакет `rsc.io/quote` и вызвать его функцию `Go`.

```go
package main

import (
    "fmt"
    "rsc.io/quote"
)

func main() {
    fmt.Println(quote.Go()) // Don't communicate by sharing memory, share memory by communicating.
}
```

Из корня пробного модуля выполните команду.

```text
go get rsc.io/quote@v1.5.2
go run .
```

В `go get` можно передать путь пакета, а Go обновит требование к модулю, из которого этот пакет взят.
Начиная с Go 1.16, обычные `go build` и `go test` по умолчанию сообщают об отсутствующей зависимости.
Требования в `go.mod` добавляют команды `go get` и `go mod tidy`. Уже выбранную версию сборка может
скачать в кеш при необходимости.

### Убрать лишнее и добавить недостающее

После изменения импортов запустите `go mod tidy`. Эта команда добавит недостающие требования, удалит
неиспользуемые и обновит `go.sum`. Она учитывает ещё и импорты в тестах, поэтому зависимость может остаться,
даже если без тестов она нигде не используется.

```text
go mod tidy
go list -m all
```

Например, удалите импорт `rsc.io/quote` и вызов `quote.Go()`, вернув предыдущий вариант программы.
После `go mod tidy` требование к этому модулю исчезнет, если он больше нигде не нужен.

### Обновить зависимость

```text
go get rsc.io/quote@v1.5.2
go get rsc.io/quote@latest
go get -u
go get -u=patch
```

- `@v1.5.2` запрашивает конкретную версию. Это может быть обновлением или понижением относительно текущей версии.
- `@latest` запрашивает новейший доступный релиз по указанному пути. Если релизов нет, Go может выбрать
  предварительную версию или версию по коммиту.
- `go get -u` обновляет модули, из которых пакет текущей папки берёт прямые и косвенные импорты. Чтобы охватить
  пакеты в подпапках, можно явно указать `go get -u ./...`.
- `go get -u=patch` обновляет такие зависимости только в рамках их текущих мажорной и минорной версий.

Модуль с путём `example.org/lib/v2` считается отдельным от `example.org/lib`. Обновление по старому пути
само по себе не переведёт программу на `/v2`. Для этого нужно изменить импорты. Версии `v0` и `v1` используют
путь без такого суффикса. При указании ветки или хеша коммита, у которого нет подходящего тега, Go запишет
**псевдоверсию**. В ней среди прочего есть время коммита и часть его хеша.

### Подключить локальную копию модуля

Допустим, проект требует `example.org/lib v1.2.0`, а рядом с проектом лежит копия библиотеки в папке `lib`.
Чтобы проверить совместные правки, можно добавить в `go.mod` следующие строки.

```go
require example.org/lib v1.2.0

replace example.org/lib => ../lib
```

Импорты в коде остаются прежними. Для этого проекта Go берёт исходники из соседней папки. В ней должен быть
свой `go.mod`, а путь `../lib` считается от каталога, где лежит файл с `replace`. Сам по себе `replace`
не добавляет зависимость. Она должна появиться среди требований.

`replace` из `go.mod` зависимости не управляет твоей сборкой. При работе с одним модулем Go читает такие
правила из `go.mod` главного модуля. Если сохранить подстановку локального пути в репозитории, у другого
разработчика для сборки должна быть такая же папка по указанному пути.

## Что могут спросить на собеседовании

### Почему Go не берёт последнюю версию при каждой сборке

Go использует **Minimal Version Selection**, или MVS. Для каждого пути модуля Go выбирает наибольшую версию
из требований, которые он прочитал для этой сборки. Если проект требует `v1.2.0`, а другая зависимость требует
тот же модуль в версии `v1.4.0`, выбрана будет `v1.4.0`. Сам факт, что где-то опубликована `v1.8.0`,
не изменит результат. Чтобы узнать, что выбрано, выполните `go list -m all`.

### Почему два проекта могут собрать один код с разными версиями

Выбор зависит от главного модуля и его требований. Например, если проект использует вашу библиотеку вместе
с другой, у той может быть более высокое требование к общей зависимости. Оба потребителя общей зависимости
в этой сборке используют выбранную Go версию по одному и тому же пути. Для разных путей, например с `/v2`
и без него, версии выбираются независимо.

### Что именно делает сборку воспроизводимой

По тем же требованиям Go выберет те же версии, а `go.sum` поможет проверить скачанные исходники. Для одинакового
результата сборки важны и версия инструмента, и целевая система, и флаги сборки. Если проект использует `replace`
на локальную папку, её содержимое тоже влияет на результат. Строка `go` в `go.mod` допускает более новые версии Go,
поэтому сама по себе она не фиксирует точный компилятор.
